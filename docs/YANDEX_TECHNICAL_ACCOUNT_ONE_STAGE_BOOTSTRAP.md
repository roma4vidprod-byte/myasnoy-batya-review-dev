# Yandex Technical Account — One-Stage Bootstrap Runbook

Status: canonical portability runbook for SLUKH / Review Activator.
Purpose: prepare a new customer technical Yandex ID in one controlled stage without repeating historical discovery work.

## Target operating model

One customer organization gets one dedicated technical Yandex ID.
The owner adds that Yandex ID as a representative of the Yandex Business organization once.
After that, SLUKH owns the technical integration lifecycle; the customer laptop is not infrastructure.

The current Meat Father account remains the development/reference account until the new technical account is ready.

## User provides only

- technical Yandex login / Yandex ID;
- customer slug;
- session account label (non-secret internal label);
- Review Activator company UUID;
- Review Activator location UUID;
- Yandex Business organization ID;
- location label;
- confirmation that representative access was granted.

Never put password, cookies, CSRF, OTP, 2FA codes, CAPTCHA data, access tokens or refresh tokens in the bootstrap profile.

## Before the one-stage bootstrap

1. Create the dedicated technical Yandex ID.
2. In Yandex Business, add it as a representative for the target organization.
3. Confirm the representative can see the target organization and reviews.
4. Copy `tools/yandex-account-bootstrap/bootstrap-profile.example.json` and fill only non-secret fields.
5. Set `representative_access` to `CONFIRMED` only after step 3.

## One-stage bootstrap sequence

Once the profile is provided and representative access is confirmed, the whole technical preparation is one stage with internal gates:

1. Validate the bootstrap profile and reject any secret-bearing key.
2. Build the immutable bootstrap bundle and record source commit + SHA-256 for every file.
3. Create a fresh server backup and capture current DB/session/reply control state.
4. Materialize the new company/location/Yandex organization scope without touching another tenant.
5. Create isolated OS/browser/session/keyring identities for the technical account.
6. Install the account-specific overlay generated by the bootstrap builder.
7. Establish the technical Yandex session through the approved interactive boundary; do not persist credentials outside encrypted storage.
8. Run read-only health: AUTH/SESSION/READ must pass before persistence.
9. Run full review read + scoped persistence and prove zero duplicates.
10. Run reply-readiness with provider write disabled and provider writes = 0.
11. Deploy the admin workflow and prove exact-scope prepare/approve/cancel/read behavior.
12. Verify hourly sync, session revision binding, backup/monitoring and reboot safety.
13. Freeze the account bootstrap evidence and stop with a report.

Any failed gate stops the stage. Roll back server/runtime changes before retrying.

## Hard write boundary

Bootstrap never authorizes a real reply POST.
Yandex reply WRITE remains 0 during account preparation.
A real reply still requires a later stage with exact review + exact text + separate approval.

## Bootstrap Pack files

- `tools/yandex-account-bootstrap/bootstrap-profile.example.json` — non-secret input contract.
- `tools/yandex-account-bootstrap/bootstrap-manifest.json` — canonical runtime, verification and parameterization file allowlist.
- `scripts/build-yandex-account-bootstrap.mjs` — offline validator/builder; no network and no credentials.
- `docs/YANDEX_TECHNICAL_ACCOUNT_ONE_STAGE_BOOTSTRAP.md` — this ordered runbook.

The builder produces:

- `ACCOUNT_PROFILE.json` — sanitized non-secret account profile;
- `BOOTSTRAP_FILES.json` — source commit and SHA-256 evidence;
- `BOOTSTRAP_PLAN.json` — ordered gates and blocked/ready state;
- `source/` — exact canonical runtime files;
- `overlay/` — account-specific scope/account-label overlay;
- `verification/` — tests needed to re-prove the account boundary;
- `reference/` — only the canonical reference documents needed for onboarding.

Historical evidence and old live-result files are deliberately excluded from the executable bundle.

## Final acceptance for the new account

- representative access is confirmed;
- session is READY and bound to the intended organization;
- hourly review sync passes independently of the customer laptop;
- full review persistence is scoped and duplicate-free;
- admin workflow reads the correct tenant only;
- reply readiness is PASS with provider writes = 0;
- no secret exists in Git/bootstrap profile/evidence;
- a backup and rollback point exist;
- all account-specific tests pass;
- the stage ends before any real reply POST.

After this acceptance, later autonomy work can move the account to Server Browser, Session Lifecycle and automatic recovery.
